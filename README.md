# Личная CRM

Приложение для контактов людей, которых знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах с датами. Контакты можно раскладывать по своим группам («Семья», «Теннис»): группы видны в списке, по ним работает фильтр и поиск. Для каждого контакта можно задать, как часто хочется общаться: на главной блок «Пора связаться» показывает, с кем связь затянулась. Идея и критерии успеха описаны в `specs/01-продуктовая-идея.md`.

## Что нужно на компьютере

- Node.js (LTS) и pnpm
- Docker Desktop — в нём работает база данных PostgreSQL
- OpenSpec — для требований к фичам. Ставится один раз на компьютер: `npm install -g @fission-ai/openspec@latest`, проверка — `openspec --version`

## Первый запуск

Все команды выполняются в папке проекта.

1. Запустите Docker Desktop и дождитесь, пока он загрузится.
2. Создайте файл `.env`: скопируйте `.env.example` и заполните значения. Если `.env` уже есть, пропустите этот шаг. Строки для входа в приложение:
   - `BETTER_AUTH_SECRET` — длинная случайная строка, секрет входа. Сделайте её в терминале командой `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` и вставьте в `.env`
   - `BETTER_AUTH_URL=http://localhost:3000` — адрес приложения на вашем компьютере
   - `SMTP_URL=smtp://localhost:1025` — куда отправлять письма со ссылкой для входа: в Mailpit (см. ниже)
   - `MAIL_FROM="Личная CRM <noreply@mail.crm.vupsen.space>"` — отправитель писем
   - `OWNER_EMAIL` — ваша настоящая почта. Все контакты, которые были в базе до появления входа, переходят пользователю с этой почтой, и под ней же создаются тестовые контакты
3. Установите зависимости:
   ```
   pnpm install
   ```
4. Запустите базу данных и Mailpit:
   ```
   pnpm db:up
   ```
5. Создайте таблицы в базе (почту владелицы команда берёт из `OWNER_EMAIL` в `.env`; если в базе уже есть контакты, а `OWNER_EMAIL` не задана, команда остановится с понятной ошибкой и ничего не изменит):
   ```
   pnpm db:migrate
   ```
6. Заполните базу тестовыми контактами (1000 штук). Скрипт сработает, только если база пустая. Контакты создаются у пользователя с почтой из `OWNER_EMAIL`, без этой строки команда остановится с ошибкой:
   ```
   pnpm db:seed
   ```
7. Запустите приложение:
   ```
   pnpm dev
   ```
8. Откройте в браузере http://localhost:3000 и войдите: введите почту из `OWNER_EMAIL`, нажмите «Получить ссылку», откройте письмо в Mailpit и нажмите в нём «Войти».

### Mailpit: письма на вашем компьютере

Mailpit — «почтовая заглушка»: приложение отправляет письма не настоящим адресатам, а в него, и наружу ничего не уходит. Это нужно, чтобы входить по ссылке без настоящей почты и не слать письма живым людям. Mailpit запускается вместе с базой командой `pnpm db:up`. Все письма, которые отправило приложение, видны на странице http://localhost:8025: откройте нужное и нажмите «Войти». Можно вводить любые адреса, даже придуманные, например `b@example.com`.

## Обычный запуск

Если всё уже настроено:

1. Запустите Docker Desktop — база поднимется сама.
2. В папке проекта выполните `pnpm dev`.
3. Откройте http://localhost:3000

Чтобы остановить приложение, нажмите `Ctrl+C` в окне терминала, где оно запущено.

| Команда | Что делает |
| --- | --- |
| `pnpm dev` | Запускает приложение в режиме разработки: изменения в коде видны сразу |
| `pnpm build` и `pnpm start` | Собирает и запускает приложение в «боевом» режиме: работает быстрее |

| `pnpm db:migrate` | Применяет миграции к базе. Почту владелицы берёт из `OWNER_EMAIL` в `.env` |
| `pnpm db:seed` | Заполняет пустую базу тестовыми контактами пользователя с почтой из `OWNER_EMAIL` в `.env` |
| `pnpm lint` | Проверяет код на ошибки |
| `pnpm format` | Приводит оформление кода к единому виду (Prettier). `pnpm format:check` — только проверяет, ничего не меняя |
| `pnpm typecheck` | Проверяет типы TypeScript |
| `pnpm test` | Запускает быстрые тесты (Vitest). Нужен запущенный Docker Desktop: тесты логики работают со своей базой `personal_crm_test` и ваши контакты не трогают |
| `pnpm test:e2e` | Запускает e2e-тесты (Playwright): собирает приложение, запускает его на порту 3100 и проходит сценарии в браузере Microsoft Edge. Нужен запущенный Docker Desktop **и Mailpit** (поднимается вместе с базой командой `pnpm db:up`): тесты входят в приложение по ссылкам из писем. Тесты работают со своей базой `personal_crm_e2e` и ваши контакты не трогают. Отчёт об упавшем тесте — `pnpm exec playwright show-report` |

### Письма автотестов

Тесты входа (`pnpm test:e2e`) отправляют письма в тот же Mailpit, что и вы при ручной проверке, и читают их через его API. Поэтому на странице http://localhost:8025 после прогона остаются письма на адреса вида `anna-…@example.com` и `e2e-user@example.com`: так и должно быть. Чтобы очистить ящик, откройте страницу и нажмите «Delete all». Быстрые тесты (`pnpm test`) письма не отправляют, отправка в них подменена. В CI Mailpit запускается отдельным сервисом в задаче Playwright (`.github/workflows/ci.yml`).

## Проверки на GitHub (CI)

Каждый PR GitHub проверяет сам: ошибки в коде (`pnpm lint`), оформление (`pnpm format:check`), типы (`pnpm typecheck`), быстрые тесты (Vitest), e2e-тесты (Playwright) на настоящей базе и сборку образа приложения. Результат — внизу страницы PR. Настройки — в `.github/workflows/ci.yml`.

Ветка `main` защищена: изменения попадают в неё только через PR и только когда все проверки зелёные. Напрямую `git push` в `main` не пройдёт. PR вливается сам после зелёных проверок, если включено автовлитие: `gh pr merge --auto --squash`.

Если проверка красная: откройте её на странице PR, там видно, что упало. Чтобы проверить заранее у себя: `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`. Оформление чинится командой `pnpm format`.

## Выкатка на сервер

Приложение работает на https://app.vupsen.space. Выкатка автоматическая:

1. Влейте PR в ветку `main`.
2. GitHub соберёт образ приложения и положит его в GitHub Container Registry (`ghcr.io/averjuli/personal-crm`) с тегом — кодом коммита.
3. Затем GitHub скопирует на сервер папку `deploy` и запустит там `crm-deploy`. Он по очереди:
   - сохраняет копию базы в `/var/backups/personal-crm` (см. «Бэкапы» ниже). Если копия не получилась, выкатка останавливается, работает прежняя версия;
   - скачивает новый образ;
   - применяет миграции базы в отдельном разовом контейнере. Если миграции упали, новая версия не запускается, работает прежняя;
   - запускает новую версию;
   - проверяет https://app.vupsen.space/health (smoke-проверка).
4. Всё вместе занимает несколько минут. Следить можно на GitHub во вкладке **Actions** или командой `gh run watch`.
5. Проверка: https://app.vupsen.space/health показывает `"status":"ok"` и номер версии — это код коммита, из которого собрано приложение.

После удачной выкатки на сервере остаются только два образа: текущий и предыдущий. Журналы контейнеров ограничены: не больше трёх файлов по 10 МБ. Ошибки запросов к базе есть только в журнале приложения, без значений запроса: сама Postgres их в свой журнал не пишет.

### Если выкатка упала

Выкатка в Actions станет красной. Сервер **сам ничего не откатывает**: если новая версия запустилась, но не отвечает, она так и остаётся запущенной. Вернуть предыдущую версию можно вручную:

```
ssh crm sudo crm-deploy rollback
```

Откат возвращает только код. Миграции базы назад не откатываются, поэтому старая версия работает с уже обновлённой базой.

**Особый случай: выкатка со входом по ссылке (миграция `0003`).** После неё у каждого контакта и группы в базе есть обязательный владелец, а версия без входа его не знает и не сможет добавить контакт. Поэтому откат этой выкатки делается **только вместе с базой**, двумя командами подряд:

1. Вернуть прежнюю версию приложения:
   ```
   ssh crm sudo crm-deploy rollback
   ```
2. Вернуть базу из копии, снятой первым шагом выкатки входа. Посмотрите список копий (`ssh crm sudo crm-deploy restore`) и возьмите самую свежую **до** времени этой выкатки: её имя `prod-<дата>-<время>-<версия>.sql.gz`, версия в имени — приложение, которое работало до выкатки входа. Дальше как в «Восстановление из бэкапа» ниже (нужен терминал, поэтому `-t`, и ввод `yes`):
   ```
   ssh -t crm sudo crm-deploy restore prod-<дата>-<время>-<версия>.sql.gz
   ```
   Восстановление поднимает приложение той версии, что работала перед ним, то есть уже прежней после шага 1.

Всё, что добавили в приложение после выкатки входа (контакты, заметки, группы, новые пользователи), при таком откате пропадёт: база возвращается на момент копии.

### Команды на сервере

| Команда | Что делает |
| --- | --- |
| `ssh crm sudo crm-deploy status` | Показывает, что запущено, текущую и предыдущую версии и отвечает ли приложение |
| `ssh crm sudo crm-deploy logs` | Последние 200 строк журнала приложения |
| `ssh crm sudo crm-deploy rollback` | Возвращает предыдущую версию |
| `ssh crm sudo crm-deploy backup` | Сохраняет копию базы в `/var/backups/personal-crm` на сервере |
| `ssh crm sudo crm-deploy restore` | Показывает список копий базы, из которых можно восстановиться |
| `ssh -t crm sudo crm-deploy restore <файл>` | Заменяет базу копией из файла, см. «Восстановление из бэкапа» |
| `ssh crm sudo crm-deploy seed` | Заполняет **пустую** базу тестовыми контактами |

### Бэкапы

Копия базы делается первым шагом каждой выкатки (и каждого отката), а также командой `ssh crm sudo crm-deploy backup`. Файлы лежат на сервере в `/var/backups/personal-crm`, читает их только root. Имя файла: `prod-<дата>-<время>-<версия>.sql.gz`, например `prod-20261103-101500-0123456789ab.sql.gz`. Версия в имени — первые 12 символов кода коммита, который работал **до** выкатки (`none` — если версии ещё не было). Хранятся последние 10 копий, старше удаляются сами. Копии `pre-restore-…` (см. ниже) сами не удаляются.

### Восстановление из бэкапа

Восстановление запускаете вы, вручную. Базу при этом удаляют и создают заново, поэтому все данные, добавленные после копии, пропадут.

1. Посмотрите список копий:
   ```
   ssh crm sudo crm-deploy restore
   ```
2. Выберите файл. Версия в имени — какой была программа, когда копию сняли. Запустите восстановление (нужен именно терминал, поэтому `-t`):
   ```
   ssh -t crm sudo crm-deploy restore prod-20261103-101500-0123456789ab.sql.gz
   ```
3. Команда покажет, какой файл и какую базу она заменит, и спросит подтверждение. Чтобы продолжить, введите `yes`; всё другое отменяет восстановление, ничего не меняется.
4. Дальше она сама:
   - сохраняет копию текущей базы в файл `pre-restore-<дата>-<время>-<версия>.sql.gz` — если восстановились не из того файла, вернитесь к нему той же командой;
   - останавливает приложение (в это время nginx показывает «Приложение временно недоступно»);
   - удаляет базу, создаёт заново и загружает копию;
   - запускает приложение **той же версии, что работала до восстановления**, и проверяет `/health`. Версию приложения восстановление не меняет.
5. Проверка: https://app.vupsen.space/health показывает `"status":"ok"` и ту же версию, что была до восстановления; данные в приложении — как на момент копии.

Если копия сделана на более старой версии, чем работает сейчас, в ней может не хватать таблиц или колонок, которые нужны новому коду. Тогда после восстановления сделайте выкатку: она применит недостающие миграции.

Если восстановление упало посреди работы, сервер сам ничего не чинит. Приложение остаётся остановленным, а в сообщении написано, где лежит копия `pre-restore-…` и какой командой к ней вернуться.

### Настройки на сервере

- На сервере приложение и база запущены в docker compose как проект `prod`.
- Пока приложение не запущено, например в момент выкатки, nginx показывает страницу «Приложение временно недоступно» из `deploy/unavailable.html`. Стили и шрифты встроены в сам файл: приложения в этот момент нет. Если поменяете цвета или шрифты в `src/app/globals.css`, поменяйте их и там.
- `/opt/personal-crm/.env` — секреты сервера, читает только root (права 600). Меняется командой `ssh -t crm "sudo nano /opt/personal-crm/.env"`. Что в нём лежит: логин, пароль и имя базы (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`; пароль после первого запуска не меняйте: база запомнила его при создании) и настройки входа: `BETTER_AUTH_SECRET` (секрет входа, длинная случайная строка), `SMTP_URL` (подключение к Resend, см. ниже) и `OWNER_EMAIL` (почта владелицы: на неё при обновлении переходят контакты, добавленные до появления входа). Пока любой из этих ключей отсутствует, выкатка останавливается на первом шаге, до копии базы, а прежняя версия продолжает работать. Остальные настройки входа не секретные и записаны в `deploy/compose.yaml`: адрес приложения `https://app.vupsen.space` и отправитель писем `Личная CRM <noreply@mail.crm.vupsen.space>`.
- **Письма со ссылкой для входа** на сервере уходят через Resend (SMTP). В `SMTP_URL` лежит `smtps://resend:<ключ>@smtp.resend.com:465`, ключ создаётся в кабинете Resend с правом только на отправку. Письма идут с домена `mail.crm.vupsen.space`: его нужно добавить в Resend и подтвердить, вписав записи DNS, которые покажет Resend, у регистратора домена (без подтверждения Resend письма не отправит). Порт 465 с сервера открыт (проверено); если когда-нибудь закроют, у Resend есть запасные 2465 и 587, меняется только `SMTP_URL`. Один и тот же образ приложения работает и на компьютере, и на сервере: куда уходят письма, решает только `SMTP_URL` (локально это Mailpit, на сервере Resend). Проверка, что письма идут: войдите на https://app.vupsen.space под своей почтой, письмо должно прийти в настоящий ящик от «Личная CRM».
- Файлы из папки `deploy` попадают на сервер сами при каждой выкатке. Вручную, с паролем sudo, нужен только `install-on-server.sh`. Его запускают при первой настройке сервера или если `crm-deploy` на сервере сломался так, что выкатка не может его обновить:
  ```
  ssh crm "rm -rf ~/personal-crm-deploy && mkdir ~/personal-crm-deploy"
  scp deploy/* crm:personal-crm-deploy/
  ssh -t crm "sudo bash ~/personal-crm-deploy/install-on-server.sh"
  ```
  Первым делом скрипт сохраняет копию базы в `/var/backups/personal-crm`.

## Где что лежит

- `src/app` — страницы: список контактов (`page.tsx`), карточка контакта (`contacts/[id]`, там же контакт удаляют; у чужого или несуществующего контакта «Контакт не найден»), новый контакт (`contacts/new`), группы (`groups`: список, переименование, удаление), вход по ссылке (`login`, а `login/expired` — «Ссылка устарела»), служебный адрес входа `api/auth`, «Такой страницы нет» (`not-found.tsx`), «Что-то пошло не так» при сбое (`error.tsx` и `global-error.tsx`)
- `src/components` — части интерфейса: форма контакта (с выбором групп), таблица, поиск и фильтр по группе
- `src/lib` — работа с контактами в базе (каждая функция берёт владельца и видит только его данные), проверка полей формы, вход (`auth.ts`: правила ссылки и лимит писем, `session.ts`: кто вошёл, `mailer.ts` и `sign-in-email.ts`: письмо)
- `src/proxy.ts` — без входа любая страница ведёт на страницу входа (настоящая проверка прав — на сервере, в каждой странице и действии)
- `src/db` — схема таблиц, подключение к базе, применение миграций (`migrations.ts`) и тестовые данные (`seed-contacts.ts`, запуск — `seed.ts`)
- `drizzle` — миграции базы данных
- `e2e` — e2e-тесты: главный сценарий из `specs/01-продуктовая-идея.md`, вход (`auth.spec.ts`), два пользователя, которые не видят данных друг друга (`two-users.spec.ts`), и подготовка тестовой базы. Настройки — в `playwright.config.ts`
- `compose.yaml` — настройки PostgreSQL в Docker на этом компьютере (порт 5433)
- `Dockerfile` — как собирается приложение для сервера
- `.github/workflows/ci.yml` — проверки каждого PR
- `.github/workflows/deploy.yml` — автоматическая выкатка после влития PR в `main`
- `deploy` — всё для сервера: приложение и база в Docker (`compose.yaml`), команда выкатки и отката (`crm-deploy.sh`), первая настройка сервера (`install-on-server.sh`), страница «Приложение временно недоступно» (`unavailable.html`)
- `src/app/health` — адрес `/health` для проверки, что приложение и база работают
- `openspec` — требования к фичам: действующие требования в `specs`, фичи в работе в `changes`, готовые в `changes/archive`. Настройки, в том числе язык (русский), — в `config.yaml`
- `.claude` — команды и навыки для Claude Code. Фичу ведут командами `/opsx:propose` (требования и план), `/opsx:apply` (реализация), `/opsx:archive` (завершение)
