# Личная CRM

Приложение для контактов людей, которых знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах с датами. Контакты можно раскладывать по своим группам («Семья», «Теннис»): группы видны в списке, по ним работает фильтр и поиск. Для каждого контакта можно задать, как часто хочется общаться: на главной блок «Пора связаться» показывает, с кем связь затянулась. Идея и критерии успеха описаны в `specs/01-продуктовая-идея.md`.

## Что нужно на компьютере

- Node.js (LTS) и pnpm
- Docker Desktop — в нём работает база данных PostgreSQL
- OpenSpec — для требований к фичам. Ставится один раз на компьютер: `npm install -g @fission-ai/openspec@latest`, проверка — `openspec --version`

## Первый запуск

Все команды выполняются в папке проекта.

1. Запустите Docker Desktop и дождитесь, пока он загрузится.
2. Создайте файл `.env`: скопируйте `.env.example` и заполните значения. Если `.env` уже есть, пропустите этот шаг. Строки для входа в приложение:
   - `BETTER_AUTH_SECRET` — длинная случайная строка, секрет входа. Сделайте её в терминале командой `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` и вставьте в `.env`
   - `BETTER_AUTH_URL=http://localhost:3000` — адрес приложения на вашем компьютере
   - `SMTP_URL=smtp://localhost:1025` — куда отправлять письма со ссылкой для входа: в Mailpit (см. ниже)
   - `MAIL_FROM="Личная CRM <noreply@mail.crm.vupsen.space>"` — отправитель писем
   - `OWNER_EMAIL` — ваша настоящая почта. Все контакты, которые были в базе до появления входа, переходят пользователю с этой почтой, и под ней же создаются тестовые контакты
3. Установите зависимости:
   ```
   pnpm install
   ```
4. Запустите базу данных и Mailpit:
   ```
   pnpm db:up
   ```
5. Создайте таблицы в базе (почту владелицы команда берёт из `OWNER_EMAIL` в `.env`; если в базе уже есть контакты, а `OWNER_EMAIL` не задана, команда остановится с понятной ошибкой и ничего не изменит):
   ```
   pnpm db:migrate
   ```
6. Заполните базу тестовыми контактами (1000 штук). Скрипт сработает, только если база пустая. Контакты создаются у пользователя с почтой из `OWNER_EMAIL`, без этой строки команда остановится с ошибкой:
   ```
   pnpm db:seed
   ```
7. Запустите приложение:
   ```
   pnpm dev
   ```
8. Откройте в браузере http://localhost:3000 и войдите: введите почту из `OWNER_EMAIL`, нажмите «Получить ссылку», откройте письмо в Mailpit и нажмите в нём «Войти».

### Mailpit: письма на вашем компьютере

Mailpit — «почтовая заглушка»: приложение отправляет письма не настоящим адресатам, а в него, и наружу ничего не уходит. Это нужно, чтобы входить по ссылке без настоящей почты и не слать письма живым людям. Mailpit запускается вместе с базой командой `pnpm db:up`. Все письма, которые отправило приложение, видны на странице http://localhost:8025: откройте нужное и нажмите «Войти». Можно вводить любые адреса, даже придуманные, например `b@example.com`.

## Обычный запуск

Если всё уже настроено:

1. Запустите Docker Desktop — база поднимется сама.
2. В папке проекта выполните `pnpm dev`.
3. Откройте http://localhost:3000

Чтобы остановить приложение, нажмите `Ctrl+C` в окне терминала, где оно запущено.

## Дни рождения

В форме контакта можно оставить дату рождения пустой, указать только день и месяц или добавить год. Неизвестный год остаётся пустым. Дату можно изменить или полностью очистить и сохранить вместе с остальными полями.

Сохранить можно только существующую календарную дату. Если год указан, дата рождения не может быть позже сегодняшней по Москве: ошибочный год вроде `20225` и завтрашняя полная дата не сохранятся. Без года можно указать любой существующий день с месяцем, в том числе ещё не наступивший в текущем году. При ошибке форма сохраняет введённое и показывает причину отказа.

На главной блок «Скоро день рождения» показывает именинников за сегодня и ещё 7 дней включительно, по московскому времени. Ближайшие даты идут сверху, при одинаковой дате — по алфавиту. В строке видны имя со ссылкой на карточку и день с месяцем, без года и возраста. Для родившихся 29 февраля в невисокосный год показывается 28 февраля; в карточке остаётся 29 февраля.

Блок расположен над «Пора связаться», скрывается при поиске и возвращается после его сброса. Фильтр группы на именинников не влияет. Если ближайших дней рождения нет, блока нет.

Проверка руками на компьютере или тест-стенде:

1. Создайте контакт с сегодняшними днём и месяцем рождения, оставив год пустым. Вернитесь на главную: контакт должен быть в «Скоро день рождения».
2. Нажмите имя в блоке и перезагрузите карточку. День и месяц должны сохраниться, год — остаться пустым.
3. Добавьте год, сохраните и перезагрузите карточку. Затем удалите только год, снова сохраните и перезагрузите: день и месяц должны остаться.
4. На главной введите имя в поиск: блок должен скрыться. Нажмите «Сбросить»: блок должен вернуться. Выберите группу, куда контакт не входит: он должен остаться среди именинников, но исчезнуть из общего списка.
5. Добавьте ещё два контакта с датой через несколько дней, один из них — с той же датой, но другим именем. Проверьте порядок по ближайшей дате и алфавиту.
6. Полностью очистите дату первого контакта и сохраните. После перезагрузки поля должны быть пустыми, а его строка в блоке — исчезнуть.
7. Повторите проверку формы и блока в узком окне: подписи, поля, имена и даты должны быть видны, без горизонтальной прокрутки.
8. Попробуйте сохранить 31 апреля, 29 февраля невисокосного года, год `20225` и завтрашнюю дату с годом. Должна появиться ошибка; после перезагрузки в карточке должны остаться прежние сохранённые данные. Сегодняшняя дата с текущим годом и декабрьская дата без года должны сохраняться.

## Полезные команды

| Команда | Что делает |
| --- | --- |
| `pnpm dev` | Запускает приложение в режиме разработки: изменения в коде видны сразу |
| `pnpm build` и `pnpm start` | Собирает и запускает приложение в «боевом» режиме: работает быстрее |
| `pnpm db:up` | Запускает в Docker базу данных и Mailpit (страница писем — http://localhost:8025) |
| `pnpm db:generate` | Готовит миграцию после изменения схемы таблиц в `src/db/schema.ts` |
| `pnpm db:migrate` | Применяет миграции к базе. Почту владелицы берёт из `OWNER_EMAIL` в `.env` |
| `pnpm db:seed` | Заполняет пустую базу тестовыми контактами пользователя с почтой из `OWNER_EMAIL` в `.env` |
| `pnpm lint` | Проверяет код на ошибки |
| `pnpm format` | Приводит оформление кода к единому виду (Prettier). `pnpm format:check` — только проверяет, ничего не меняя |
| `pnpm typecheck` | Проверяет типы TypeScript |
| `pnpm test` | Запускает быстрые тесты (Vitest). Нужен запущенный Docker Desktop: тесты логики работают со своей базой `personal_crm_test` и ваши контакты не трогают |
| `pnpm test:e2e` | Запускает e2e-тесты (Playwright): собирает приложение, запускает его на порту 3100 и проходит сценарии в браузере Microsoft Edge. Нужен запущенный Docker Desktop **и Mailpit** (поднимается вместе с базой командой `pnpm db:up`): тесты входят в приложение по ссылкам из писем. Тесты работают со своей базой `personal_crm_e2e` и ваши контакты не трогают. Отчёт об упавшем тесте — `pnpm exec playwright show-report` |

### Письма автотестов

Тесты входа (`pnpm test:e2e`) отправляют письма в тот же Mailpit, что и вы при ручной проверке, и читают их через его API. Поэтому на странице http://localhost:8025 после прогона остаются письма на адреса вида `anna-…@example.com` и `e2e-user@example.com`: так и должно быть. Чтобы очистить ящик, откройте страницу и нажмите «Delete all». Быстрые тесты (`pnpm test`) письма не отправляют, отправка в них подменена. В CI Mailpit запускается отдельным сервисом в задаче Playwright (`.github/workflows/ci.yml`).

## Проверки на GitHub (CI)

Каждый PR GitHub проверяет сам: ошибки в коде (`pnpm lint`), оформление (`pnpm format:check`), типы (`pnpm typecheck`), быстрые тесты (Vitest), e2e-тесты (Playwright) на настоящей базе и сборку образа приложения. Результат — внизу страницы PR. Настройки — в `.github/workflows/ci.yml`.

Ветка `main` защищена: изменения попадают в неё только через PR и только когда все проверки зелёные. Напрямую `git push` в `main` не пройдёт. PR вливается сам после зелёных проверок, если включено автовлитие: `gh pr merge --auto --squash`.

Если проверка красная: откройте её на странице PR, там видно, что упало. Чтобы проверить заранее у себя: `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`. Оформление чинится командой `pnpm format`.

## Выкатка на сервер

Приложение работает на https://app.vupsen.space. После merge в `main` workflow **Deploy** собирает образ с тегом SHA коммита, публикует его в `ghcr.io/averjuli/personal-crm` и выкатывает на тест-стенд. Он копирует всю папку `deploy/` на сервер, применяет миграции в разовом контейнере, запускает приложение и проверяет `/health`.

Прод выкатываете вы кнопкой в отдельном workflow **Deploy prod**. На прод едет образ, уже проверенный на тест-стенде.

### Выкатить на прод

1. Дождитесь зелёной задачи **Deploy staging** в workflow **Deploy** и проверьте приложение на https://test-app.vupsen.space.
2. Откройте репозиторий на GitHub → **Actions** → **Deploy prod** → **Run workflow**.
3. Выберите ветку `main`. Оставьте поле **sha** пустым — workflow выберет SHA последней успешной выкатки тест-стенда. В запасном варианте вставьте полный SHA из 40 символов. Workflow проверит его по успешным задачам выкатки тест-стенда в истории GitHub.
4. Галочка **rollback** должна быть снята. Нажмите **Run workflow**.
5. Скрипт обновит папку `deploy/` на сервере и выполнит выкатку прода по шагам.
   - Сохранит копию базы. Ошибка бэкапа останавливает выкатку.
   - Скачает выбранный образ, если его ещё нет на сервере.
   - Применит миграции в разовом контейнере из этого же образа. Ошибка миграции останавливает запуск новой версии.
   - Запустит новую версию и проверит https://app.vupsen.space/health.
   - После успешной проверки почистит старые образы сервера и GHCR.
6. Откройте **Summary** завершившегося запуска. Там указан фактический SHA выкатки и ссылка на проверку тест-стенда.
7. Проверьте https://app.vupsen.space/health — ожидаются `"status":"ok"` и тот же SHA в `version`. Откройте приложение, войдите по ссылке из письма и проверьте список и карточку контакта.

### Откатить прод

1. Откройте **Actions** → **Deploy prod** → **Run workflow**, выберите `main`.
2. Включите галочку **rollback** и нажмите **Run workflow**. Сервер возьмёт предыдущую версию прода из своего файла `previous-version`. При включённой галочке значение **sha** игнорируется, проверка тест-стенда пропускается.
3. Скрипт сохранит бэкап базы, применит миграции выбранного образа, запустит его и проверит `/health`. Образ предыдущей версии хранится на сервере, поэтому откат может использовать его при недоступном GHCR.
4. В **Summary** будет указан фактический SHA отката. Сверьте его с `version` на https://app.vupsen.space/health и проверьте вход и контакты.

Откат возвращает версию приложения. База сохраняет уже применённые миграции. Если старая версия требует прежнюю структуру базы, понадобится восстановление подходящего бэкапа по инструкции ниже.

### Если выкатка упала

Выкатка в Actions станет красной. После ошибки бэкапа или миграции продолжает работать прежняя версия приложения. После ошибки запуска или smoke-проверки новая версия может уже работать на сервере. Решение об откате принимаете вы и запускаете **Deploy prod** с галочкой **rollback**.

Если красным стал шаг чистки GHCR, выкатка приложения уже прошла smoke-проверку. Фактический SHA смотрите в **Summary**, состояние приложения — на `/health`. Ошибка чистки остаётся видна в запуске и требует исправления причины.

**Особый случай: выкатка со входом по ссылке (миграция `0003`).** После неё у каждого контакта и группы в базе есть обязательный владелец, а версия без входа его не знает и не сможет добавить контакт. Поэтому откат этой выкатки делается **только вместе с базой**, двумя шагами подряд:

1. Вернуть прежнюю версию приложения через **Deploy prod** с галочкой **rollback**, как описано выше.
2. Вернуть базу из копии, снятой первым шагом выкатки входа. Посмотрите список копий (`ssh crm sudo crm-deploy restore prod`) и возьмите самую свежую **до** времени этой выкатки: её имя `prod-<дата>-<время>-<версия>.sql.gz`, версия в имени — приложение, которое работало до выкатки входа. Дальше как в «Восстановление из бэкапа» ниже (нужен терминал, поэтому `-t`, и ввод `yes`):
   ```
   ssh -t crm sudo crm-deploy restore prod prod-<дата>-<время>-<версия>.sql.gz
   ```
   Восстановление поднимает приложение той версии, что работала перед ним, то есть уже прежней после шага 1.

Всё, что добавили в приложение после выкатки входа (контакты, заметки, группы, новые пользователи), при таком откате пропадёт: база возвращается на момент копии.

### Команды на сервере

| Команда | Что делает |
| --- | --- |
| `ssh crm sudo crm-deploy status prod` | Показывает, что запущено, текущую и предыдущую версии prod и отвечает ли приложение |
| `ssh crm sudo crm-deploy logs prod` | Последние 200 строк журнала приложения prod |
| `ssh crm sudo crm-deploy backup prod` | Сохраняет копию базы prod в `/var/backups/personal-crm` на сервере |
| `ssh crm sudo crm-deploy backup prod daily` | Сохраняет копию в ежедневную серию бэкапов, например для ручной проверки |
| `ssh crm sudo crm-deploy restore prod` | Показывает список копий базы prod, из которых можно восстановиться |
| `ssh -t crm sudo crm-deploy restore prod <файл>` | Заменяет базу prod копией из файла, см. «Восстановление из бэкапа» |
| `ssh crm sudo crm-deploy seed prod` | Заполняет **пустую** базу prod тестовыми контактами |

Логи контейнеров лежат в системном журнале `journald`, размер ограничивает система. Ошибки запросов к базе есть только в журнале приложения, без значений запроса: сама Postgres их в свой журнал не пишет.

### Бэкапы

Копия базы создаётся каждый день в **03:00 по Москве**, перед каждой выкаткой и откатом прода, а также по команде `ssh crm sudo crm-deploy backup prod`. Расписание устанавливается автоматически при выкатке обновлённой папки `deploy/` на тест-стенд или прод. На сервере работают `personal-crm-backup.timer` и `personal-crm-backup.service`. После простоя сервера таймер выполняет пропущенный запуск.

Файлы лежат в `/var/backups/personal-crm`, права — `600`, читает их только root. Ежедневные и предвыкаточные копии хранятся отдельными сериями по 7 файлов.

- `daily-<дата>-<время>-<версия>.sql.gz` — ежедневные копии.
- `prod-<дата>-<время>-<версия>.sql.gz` — копии перед выкаткой или откатом и ручные копии.
- `pre-restore-…` — копии перед восстановлением, сохраняются до ручного удаления.

Дата и время новых копий указаны по Москве, время включает доли секунды для уникальности имени. Версия — первые 12 символов SHA приложения, работавшего в момент копии (`none` — если версии ещё не было). Готовый файл появляется после завершения и проверки архива.

После первой выкатки этой доработки проверьте расписание и создание копии.

```sh
ssh crm sudo systemctl list-timers personal-crm-backup.timer
ssh crm sudo crm-deploy backup prod daily
ssh crm sudo crm-deploy restore prod
```

В списке таймеров должно быть следующее срабатывание в 03:00 по Москве с учётом часового пояса сервера. Команда бэкапа должна вывести имя `daily-…sql.gz`, а команда списка — показать этот файл. После следующего ежедневного запуска проверьте появление новой копии и результат службы командой `ssh crm sudo systemctl show personal-crm-backup.service -p Result -p ExecMainStatus` — ожидаются `Result=success` и `ExecMainStatus=0`.

### Чистка образов

После успешного smoke прода скрипт удаляет образы **этого приложения** старше двух недель. Сохраняются текущая и предыдущая версии прода и текущая версия тест-стенда. Чистка ждёт завершения выкатки тест-стенда, чтобы сохранить его образ. Эти версии доступны для ручного отката.

В GHCR после успешной выкатки прода сохраняются 10 последних сборок с SHA-тегами и все необходимые им части образа. Свежие части ещё публикуемых сборок также сохраняются. Чистка ограничена пакетом `personal-crm`. Результат виден в шаге **Keep the latest ten registry builds** и в **Summary**. Workflow использует свой `GITHUB_TOKEN` с правами `packages: write`, а репозиторий должен иметь роль администратора своего пакета. Для образов, опубликованных этим репозиторием, GitHub выдаёт эту роль автоматически. [Права удаления пакетов в GitHub](https://docs.github.com/en/packages/learn-github-packages/deleting-and-restoring-a-package).

### Восстановление из бэкапа

Восстановление запускаете вы, вручную. Базу при этом удаляют и создают заново, поэтому все данные, добавленные после копии, пропадут.

1. Посмотрите список копий:
   ```
   ssh crm sudo crm-deploy restore prod
   ```
2. Выберите файл. Версия в имени — какой была программа, когда копию сняли. Запустите восстановление (нужен именно терминал, поэтому `-t`):
   ```
   ssh -t crm sudo crm-deploy restore prod prod-20261103-101500-0123456789ab.sql.gz
   ```
3. Команда покажет, какой файл и какую базу она заменит, и спросит подтверждение. Чтобы продолжить, введите `yes`; всё другое отменяет восстановление, ничего не меняется.
4. Дальше она сама:
   - сохраняет копию текущей базы в файл `pre-restore-<дата>-<время>-<версия>.sql.gz` — если восстановились не из того файла, вернитесь к нему той же командой;
   - останавливает приложение (в это время nginx показывает «Приложение временно недоступно»);
   - удаляет базу, создаёт заново и загружает копию;
   - запускает приложение **той же версии, что работала до восстановления**, и проверяет `/health`. Версию приложения восстановление не меняет.
5. Проверка: https://app.vupsen.space/health показывает `"status":"ok"` и ту же версию, что была до восстановления; данные в приложении — как на момент копии.

Если копия сделана на более старой версии, чем работает сейчас, в ней может не хватать таблиц или колонок, которые нужны новому коду. Тогда после восстановления сделайте выкатку: она применит недостающие миграции.

Если восстановление упало посреди работы, сервер сам ничего не чинит. Приложение остаётся остановленным, а в сообщении написано, где лежит копия `pre-restore-…` и какой командой к ней вернуться.

### Настройки на сервере

- На сервере приложение и база запущены в docker compose как проект `prod`.
- Пока приложение не запущено, например в момент выкатки, nginx показывает страницу «Приложение временно недоступно» из `deploy/unavailable.html`. Стили и шрифты встроены в сам файл: приложения в этот момент нет. Если поменяете цвета или шрифты в `src/app/globals.css`, поменяйте их и там.
- `/opt/personal-crm/.env` — секреты сервера, читает только root (права 600). Меняется командой `ssh -t crm "sudo nano /opt/personal-crm/.env"`. Что в нём лежит: логин, пароль и имя базы (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`; пароль после первого запуска не меняйте: база запомнила его при создании) и настройки входа: `BETTER_AUTH_SECRET` (секрет входа, длинная случайная строка), `SMTP_URL` (подключение к Resend, см. ниже) и `OWNER_EMAIL` (почта владелицы: на неё при обновлении переходят контакты, добавленные до появления входа). Пока любой из этих ключей отсутствует, выкатка останавливается на первом шаге, до копии базы, а прежняя версия продолжает работать. Остальные настройки входа не секретные и записаны в `deploy/compose.yaml`: адрес приложения `https://app.vupsen.space` и отправитель писем `Личная CRM <noreply@mail.crm.vupsen.space>`.
- **Письма со ссылкой для входа** на сервере уходят через Resend (SMTP). В `SMTP_URL` лежит `smtps://resend:<ключ>@smtp.resend.com:465`, ключ создаётся в кабинете Resend с правом только на отправку. Письма идут с домена `mail.crm.vupsen.space`: его нужно добавить в Resend и подтвердить, вписав записи DNS, которые покажет Resend, у регистратора домена (без подтверждения Resend письма не отправит). Порт 465 с сервера открыт (проверено); если когда-нибудь закроют, у Resend есть запасные 2465 и 587, меняется только `SMTP_URL`. Один и тот же образ приложения работает и на компьютере, и на сервере: куда уходят письма, решает только `SMTP_URL` (локально это Mailpit, на сервере Resend). Проверка, что письма идут: войдите на https://app.vupsen.space под своей почтой, письмо должно прийти в настоящий ящик от «Личная CRM».
- Файлы из папки `deploy` попадают на сервер сами при каждой выкатке. Вручную, с паролем sudo, нужен только `install-on-server.sh`. Его запускают при первой настройке сервера или если `crm-deploy` на сервере сломался так, что выкатка не может его обновить:
  ```
  ssh crm "rm -rf ~/personal-crm-deploy && mkdir ~/personal-crm-deploy"
  scp deploy/* crm:personal-crm-deploy/
  ssh -t crm "sudo bash ~/personal-crm-deploy/install-on-server.sh"
  ```
  Первым делом скрипт сохраняет копию базы в `/var/backups/personal-crm`.

## Тестовый стенд

Стенд доступен по адресу `https://test-app.vupsen.space`. Его контейнеры и база работают в Compose-проекте `staging`, настройки лежат отдельно от prod в `/opt/personal-crm/staging/.env`. При первом deploy staging база автоматически копируется из последнего прод-бэкапа. Выкатка образа не делает копию базы.

Перед первой настройкой заполните отдельный файл окружения на сервере. Не копируйте `.env` prod: задайте новые логин, пароль базы и `BETTER_AUTH_SECRET`; `SMTP_URL` должен содержать отдельный ключ отправки почты.

```sh
ssh -t crm "sudo install -d -m 700 /opt/personal-crm/staging"
ssh -t crm "sudo nano /opt/personal-crm/staging/.env"
```

Добавьте строки, подставив свои значения:

```dotenv
POSTGRES_USER=
POSTGRES_PASSWORD=
POSTGRES_DB=
BETTER_AUTH_SECRET=
SMTP_URL=
OWNER_EMAIL=
BETTER_AUTH_URL=https://test-app.vupsen.space
APP_PORT=3002
APP_MEMORY_LIMIT=512m
DB_MEMORY_LIMIT=512m
```

Затем установите права файла: `ssh crm "sudo chmod 600 /opt/personal-crm/staging/.env"`.

Для HTTPS в DNS должна быть A-запись `test-app.vupsen.space` на IP сервера. При первой выкатке workflow сначала передаст скрипты, затем проверит наличие TLS-сертификата и пароля; если настройка ещё не завершена, staging deploy остановится до изменения базы и приложения. После этого запустите `ssh -t crm sudo crm-deploy setup-staging`; команда спросит логин и пароль Basic Auth (пароль вводится без отображения) и выпустит TLS-сертификат. Она добавляет только отдельный nginx сайт и свои файлы. Затем повторите staging job в GitHub Actions.

При первом deploy скрипт сам загружает самую свежую готовую копию `prod-*.sql.gz` или `daily-*.sql.gz` в новую staging базу. Если нужно создать базу до первого deploy, запустите `ssh crm sudo crm-deploy staging-init staging`. Для обновления тестовых данных подтвердите замену staging базы: `ssh -t crm sudo crm-deploy staging-refresh staging`.

После merge в `main` SHA автоматически выкатывается на staging. Выкатку проверенного SHA на прод запускаете вы через **Deploy prod**. Проверить стенд: откройте `https://test-app.vupsen.space`, войдите с Basic Auth, запросите magic link и проверьте, что письмо ведёт на этот же адрес; `/health` на сервере проверяется deploy-скриптом. Статус и логи: `ssh crm sudo crm-deploy status staging` и `ssh crm "sudo journalctl -n 200 CONTAINER_NAME=staging-app-1"`. Ручной откат: `ssh crm sudo crm-deploy rollback staging`.

## Где что лежит

- `src/app` — страницы: список контактов (`page.tsx`), карточка контакта (`contacts/[id]`, там же контакт удаляют; у чужого или несуществующего контакта «Контакт не найден»), новый контакт (`contacts/new`), группы (`groups`: список, переименование, удаление), вход по ссылке (`login`, а `login/expired` — «Ссылка устарела»), служебный адрес входа `api/auth`, «Такой страницы нет» (`not-found.tsx`), «Что-то пошло не так» при сбое (`error.tsx` и `global-error.tsx`)
- `src/components` — части интерфейса: форма контакта (с выбором групп), таблица, поиск и фильтр по группе
- `src/lib` — работа с контактами в базе (каждая функция берёт владельца и видит только его данные), проверка полей формы, вход (`auth.ts`: правила ссылки и лимит писем, `session.ts`: кто вошёл, `mailer.ts` и `sign-in-email.ts`: письмо)
- `src/proxy.ts` — без входа любая страница ведёт на страницу входа (настоящая проверка прав — на сервере, в каждой странице и действии)
- `src/db` — схема таблиц, подключение к базе, применение миграций (`migrations.ts`) и тестовые данные (`seed-contacts.ts`, запуск — `seed.ts`)
- `drizzle` — миграции базы данных
- `e2e` — e2e-тесты: главный сценарий из `specs/01-продуктовая-идея.md`, вход (`auth.spec.ts`), два пользователя, которые не видят данных друг друга (`two-users.spec.ts`), и подготовка тестовой базы. Настройки — в `playwright.config.ts`
- `compose.yaml` — настройки PostgreSQL в Docker на этом компьютере (порт 5433)
- `Dockerfile` — как собирается приложение для сервера
- `.github/workflows/ci.yml` — проверки каждого PR
- `.github/workflows/deploy.yml` — сборка образа и автоматическая выкатка на тест-стенд после влития PR в `main`
- `.github/workflows/deploy-prod.yml` — ручная выкатка и откат прода
- `deploy` — всё для выкатки и сервера. `ci-deploy.sh` передаёт скрипты и вызывает серверную команду, `github-release.py` выбирает проверенный SHA и чистит GHCR, `crm-deploy.sh` управляет выкаткой, бэкапами и восстановлением, `personal-crm-backup.service` и `.timer` задают ежедневный бэкап. Здесь же `compose.yaml`, первая настройка сервера (`install-on-server.sh`) и страница «Приложение временно недоступно» (`unavailable.html`)
- `src/app/health` — адрес `/health` для проверки, что приложение и база работают
- `openspec` — требования к фичам: действующие требования в `specs`, фичи в работе в `changes`, готовые в `changes/archive`. Настройки, в том числе язык (русский), — в `config.yaml`
- `.claude` — команды и навыки для Claude Code. Фичу ведут командами `/opsx:propose` (требования и план), `/opsx:apply` (реализация), `/opsx:archive` (завершение)
