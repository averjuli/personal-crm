# Design

## Context

Зачем это нужно - см. `proposal.md`, раздел Why; что должно работать - спеки `specs/contact-notes` и `specs/keep-in-touch`.

Что есть сейчас:

- Одна таблица `contacts` (`src/db/schema.ts`). Заметки - колонка `notes` (text, до 20 000 символов), редактируется вместе со всей карточкой одной формой `ContactForm` (`src/components/contact-form.tsx`) и сохраняется действием `updateContactAction`. Даты у заметок нет; в тестовых данных дата вписана в текст строки (`12.03.2025: ...`).
- Работа с базой - только с сервера: `src/lib/contacts.ts` (`server-only`), серверные действия в `src/app/contacts/actions.ts`, после изменений - `revalidatePath("/", "layout")`.
- Проверка форм - zod (`src/lib/contact-form.ts`); при ошибке форма получает введённые значения обратно.
- Главная (`src/app/page.tsx`) - заголовок, поиск, счётчик, таблица `ContactsTable` (клиентский компонент, стили в `globals.css`, колонки скрываются по ширине экрана через `nth-child`). На странице до 1000 контактов.
- Диалог подтверждения удаления уже есть: `DeleteContactButton` на `AlertDialog` (shadcn/ui поверх `@base-ui/react`).
- Миграции: drizzle-kit генерирует SQL в `drizzle/`, на сервере `crm-deploy` применяет их разовым контейнером до старта нового образа. Ручной откат `crm-deploy rollback` запускает предыдущий образ на той же базе, миграции назад не откатываются.
- PostgreSQL 18. Тестов и тестовой библиотеки в проекте нет.
- Next.js 16.4.2 отличается от привычного: перед кодом серверных действий и форм свериться с `node_modules/next/dist/docs/01-app/02-guides/forms.md` и `server-actions.md`.

## Goals / Non-Goals

**Goals:**

- Срок и просрочка считаются в одном месте - в SQL, одинаково для блока «Пора связаться» и для карточки.
- Миграция переносит старые заметки без потерь, в одной транзакции со сменой схемы.
- Ручной откат на предыдущий образ после выкатки не ломает приложение.
- Без новых библиотек.

**Non-Goals:**

- Удаление старой колонки `contacts.notes` - отдельным изменением, когда новая версия поработает.
- Автотесты: для них нужна новая библиотека, это отдельное решение. Проверка - `pnpm lint`, `pnpm build` и ручные сценарии из спек.
- Разбор старого текста заметок на отдельные записи по датам внутри текста.
- Ограничение длины блока «Пора связаться» или постраничный вывод.

## Decisions

### 1. Заметки - отдельная таблица `notes`

Поля: `id` (identity), `contact_id` (FK на `contacts.id`, `on delete cascade`), `body` (text, not null), `noted_on` (`date`, not null - день общения), `created_at`, `updated_at` (timestamptz). Индекс `(contact_id, noted_on desc, id desc)` - под ленту в карточке и под `max(noted_on)` по контакту.

Порядок ленты: `noted_on desc, id desc` - при одной дате выше добавленная позже.

`noted_on` - тип `date` и строка `YYYY-MM-DD` в коде (режим `string` у Drizzle), а не timestamp: у заметки по спеке есть только день. Строка не сдвигается часовыми поясами при передаче в браузер.

Каскадное удаление закрывает требование «заметки удаляются вместе с контактом» без изменений в `deleteContact`.

Альтернатива - JSON-массив заметок в колонке контакта: проще миграция, но сложнее считать последнюю дату, сортировать и править одну заметку.

### 2. Частота, отметка и пропуск - четыре колонки в `contacts`

- `contact_frequency` - text с ограничением `check (contact_frequency in ('week', 'month', 'quarter', 'year'))`, null - «Не задано». В TypeScript - `text({ enum: [...] })`. Подписи для интерфейса («Раз в неделю» и т. д.) - в одном месте, `src/lib/keep-in-touch.ts`.
- `frequency_set_on` - `date`, день, когда частоту задали. Ограничение: `(contact_frequency is null) = (frequency_set_on is null)`.
- `contacted_on` - `date`, день последней отметки «Уже связался», null - не отмечали. Одна дата, а не история: новая отметка заменяет прежнюю, история общения - это заметки.
- `skipped_on` - `date`, день последнего пропуска («Пропустить этот раз»). Ограничение: `skipped_on is null or contact_frequency is not null`.

Text с check, а не `pgEnum`: новый вариант частоты позже - это правка check, без `ALTER TYPE`.

Правило дня отсчёта - одним `UPDATE` без предварительного чтения:
`frequency_set_on = case when <new> is null then null when contact_frequency is null then <today> else frequency_set_on end`. При создании контакта с частотой - сегодня. При «Не задано» тот же `UPDATE` обнуляет `skipped_on`: иначе старый пропуск сразу сделал бы контакт просроченным, когда частоту зададут снова. `contacted_on` не трогается: это факт общения, как заметка.

Альтернативы для галочки: создавать заметку «Связались» - пользователь выбрал отметку без заметки; отдельная таблица отметок с историей - лишняя, историю ведут заметки.

### 3. Последнее общение и срок не хранятся, а считаются в SQL

Одно SQL-выражение в `src/lib/keep-in-touch.ts`, общее для двух запросов:

- последнее общение `last_contact_on = greatest(max(notes.noted_on), contacted_on)` по контакту (`greatest` в PostgreSQL пропускает null);
- точка отсчёта `coalesce(greatest(last_contact_on, skipped_on), frequency_set_on)`;
- срок `due_on = (точка отсчёта + interval)::date`, где interval по частоте: `7 days`, `1 month`, `3 months`, `1 year`. PostgreSQL сам прижимает к концу месяца: 31 января + 1 месяц = 28 февраля;
- просрочка в днях `today - due_on`; контакт просрочен, если она `>= 0`.

Запрос блока: контакты с частотой, `due_on <= today`, порядок `due_on asc`, затем имя (`collate "ru-x-icu"`, как в общем списке), затем `id`. Запрос карточки (`getContact`) получает `last_contact_on`, `due_on` и просрочку тем же выражением.

Альтернатива - хранить дату последней заметки в `contacts` и обновлять при каждой правке заметки: быстрее чтение, но значение может разойтись с заметками при любой ошибке в коде. Для тысяч контактов с индексом подсчёт дешёвый.

### 4. Часовой пояс - Москва, в одной константе

`APP_TIME_ZONE = "Europe/Moscow"`. «Сегодня» в SQL - `(now() at time zone 'Europe/Moscow')::date`, в TypeScript - через `Intl.DateTimeFormat` с `timeZone`. Сервер и база могут жить в UTC; ни один расчёт не опирается на пояс процесса.

Даты для показа («12 октября 2026») форматируются из строки `YYYY-MM-DD` через `Intl.DateTimeFormat("ru-RU", { timeZone: "UTC" })`, чтобы день не съехал. Окончания «день / дня / дней» - через `Intl.PluralRules("ru")`.

### 5. Проверка заметок - zod, как у контакта

`src/lib/note-form.ts`: текст - trim, не пустой («Напишите текст заметки»), не больше 20 000 символов; дата - обязательна («Укажите дату»), корректная `YYYY-MM-DD`, не позже сегодняшнего дня по Москве («Дата не может быть позже сегодняшней»). При ошибке действие возвращает введённые значения, как `parseContactForm`.

В браузере у поля даты `max` = сегодня, но решает проверка на сервере.

### 6. Серверные действия

В `src/app/contacts/actions.ts` (или рядом, `notes-actions.ts`, если файл разрастётся):

- `createContactAction` - контакт и первая заметка (поле `note` формы, дата - сегодня) в одной транзакции; частота с днём отсчёта.
- `updateContactAction` - без заметок, с частотой (правило из решения 2).
- `addNoteAction(contactId)`, `updateNoteAction(noteId)`, `deleteNoteAction(noteId)` - проверка id как в существующих действиях; не нашли контакт или заметку - сообщение «Эта заметка не найдена» / «Этот контакт не найден».
- `markContactedAction(contactId)` и `skipContactAction(contactId)` - ставят `contacted_on` или `skipped_on` в сегодняшний день и возвращают прежнее значение для отмены. Повторное нажатие в тот же день ничего не меняет.
- `undoKeepInTouchAction(contactId, kind, previous, applied)` - возвращает прежнее значение, только если в поле всё ещё стоит то, что поставило нажатие (`where contacted_on is not distinct from <applied>`): отмена не сотрёт более новую отметку.

Все действия после изменений вызывают `revalidatePath("/", "layout")`: обновляются и лента в карточке, и строки «Последнее общение / Пора связаться», и блок на главной.

Старая колонка `contacts.notes` остаётся в Drizzle-схеме с комментарием, что она устарела и оставлена для отката; новый код её не читает и не пишет. Иначе drizzle-kit сгенерирует её удаление.

### 7. Интерфейс

- **Поле частоты** - компонент `Select` из shadcn/ui (стиль `base-nova`, поверх уже установленного `@base-ui/react`), в той же «карточке поля», что остальные поля `ContactForm`; значение уходит в форму через `name="frequency"`. Альтернативы: стандартный `<select>` выглядит чужеродно рядом с остальными полями; ряд кнопок-переключателей на пять вариантов не помещается на телефоне. Если `shadcn add select` потянет новый пакет - остановиться и спросить.
- **Строки срока в карточке** - под полем частоты, серверные данные из `getContact`: «Последнее общение: …» или «Заметок ещё не было»; при частоте - «Пора связаться: <дата>», «пора сегодня» или «просрочено на N дней».
- **Блок «Заметки»** в карточке - между формой контакта и кнопкой «Удалить контакт». Клиентский компонент: форма добавления (textarea, `<input type="date">`, «Добавить заметку»), лента заметок. У заметки - «Изменить» (правка на месте, «Сохранить» / «Отмена») и «Удалить» (диалог по образцу `DeleteContactButton`). Поле даты и все цвета - через существующие токены.
- **Форма нового контакта** - поле «Заметка» на месте прежнего «Заметки»; в форме правки его нет.
- **Блок «Пора связаться»** на главной - серверный компонент между заголовком и поиском, рисуется только без поискового запроса. Строка: имя ссылкой на карточку, частота, просрочка. Пусто - «Со всеми на связи».
- **Галочка, крестик и отмена** - строки блока рисует клиентский компонент. Справа в строке две кнопки-значка 44×44 (`Check` и `X` из lucide) с `aria-label` и `title` «Уже связался» / «Пропустить этот раз». После нажатия строка сразу заменяется строкой «Отметили: <имя>» / «Пропустили: <имя>» с кнопкой «Отменить» на 5 секунд. После действия сервер обновляет список, и контакта в нём уже нет. Поэтому строки отмены компонент держит в своём состоянии вместе с местом в списке и вставляет на то же место. «Отменить» вызывает действие отмены; после обновления контакт возвращается в список. Пока запрос идёт, кнопки строки заблокированы.
- **Колонка «Как часто»** в `ContactsTable` - второй после имени, видна с `md`, как телефон; правила `nth-child` в `globals.css` сдвигаются на одну колонку.

### 8. Тестовые данные

`src/db/seed.ts` пишет заметки в `notes` с датами за последние два года (вместо дат в тексте) и задаёт частоту примерно 5% контактов с днём отсчёта в прошлом, чтобы локально блок «Пора связаться» был не пустым. Отметки «Уже связался» и пропуски seed не ставит: их проверяют руками кнопками блока. Seed по-прежнему работает только на пустой базе; на уже заполненной локальной базе старые заметки перенесёт миграция.

## Risks / Trade-offs

- [Миграция переносит данные на сервере] → Перед выкаткой - бэкап `ssh crm sudo crm-deploy backup`. Перенос и смена схемы в одной транзакции: упала миграция - новый образ не стартует, база как была.
- [Ручной откат после выкатки] → Схема меняется только добавлением: новая таблица, новые колонки с null, старая колонка `notes` на месте. Предыдущий образ работает, но не видит заметки, добавленные после выкатки, и показывает старый текст заметок. Если во время отката правили заметки в старой версии, после повторной выкатки эти правки не перенесутся сами - перенести руками.
- [Москва зашита как часовой пояс] → Если пользователь живёт в другом поясе, «сегодня» сменится на несколько часов раньше или позже полуночи. Пояс в одной константе - поменять легко.
- [Старые заметки получают дату последнего сохранения карточки] → Дата неточная: карточку могли сохранять из-за телефона. Это решение пользователя; контакты со старыми заметками после выбора частоты могут сразу оказаться в блоке.
- [Отмена живёт 5 секунд и только на открытой странице] → Ошибочную галочку или крестик, замеченные позже, в интерфейсе не исправить. Вред небольшой: контакт сам вернётся в блок через период. Если понадобится исправлять позже - отдельная доработка.
- [Двойное нажатие или нажатие в двух вкладках] → Кнопки блокируются на время запроса; повторная отметка в тот же день ничего не меняет; отмена сверяет значение и не трогает чужую, более новую отметку.
- [Блок «Пора связаться» без ограничения длины] → Частоту задают вручную, список ожидается коротким. Если станет длинным - отдельная доработка.
- [Ленту заметок грузим целиком] → Заметок у одного человека десятки, не тысячи; постраничный вывод не нужен.

## Migration Plan

1. Локально: изменить схему, `pnpm db:generate`, дописать в конец сгенерированного SQL перенос:
   `insert into notes (contact_id, body, noted_on, created_at, updated_at) select id, notes, (updated_at at time zone 'Europe/Moscow')::date, updated_at, updated_at from contacts where notes ~ '\S'`.
   Текст переносится как есть; поле без единого непробельного символа пропускается.
2. Локально: `pnpm db:migrate` на базе с данными, сверить число заметок с числом контактов с непустыми заметками.
3. Перед merge: бэкап базы на сервере.
4. Merge PR → CI собирает образ → `crm-deploy`: миграции разовым контейнером → новый образ → smoke `/health`.
5. Проверка руками на app.vupsen.space по сценариям спек.
6. Откат - только вручную, запускает пользователь: `ssh crm sudo crm-deploy rollback`.
