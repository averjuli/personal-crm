# Design

## Context

Сейчас в базе `contacts` и `notes` (`src/db/schema.ts`). Главная страница (`src/app/page.tsx`) читает `?q=`, `listContacts(search)` ищет по имени через `ilike`; таблица `ContactsTable` - клиентский компонент с лёгкими строками (список до 1000 контактов). Форма контакта (`contact-form.tsx`) - `useActionState` + server action, данные разбирает zod (`contact-form.ts`). Мотивацию см. в proposal.md.

## Goals / Non-Goals

**Goals:**
- Группы как отдельная сущность, связь «многие ко многим» с контактами.
- Список остаётся быстрым: группы подтягиваются без запроса на каждую строку.

**Non-Goals:**
- Цвета и иконки групп, порядок групп вручную, вложенные группы.
- Фильтр по нескольким группам сразу.
- Влияние групп на «Пора связаться».

## Decisions

**Таблицы.** `groups` (`id`, `name`, `created_at`) и `contact_groups` (`contact_id`, `group_id`, составной первичный ключ, оба внешних ключа `on delete cascade`). Каскад даёт нужное поведение: удалили группу - связи ушли, контакты остались; удалили контакт - он пропал из групп. Индекс по `group_id` для фильтра. Альтернатива - массив названий в колонке контакта: проще, но переименование и подсчёт контактов превращаются в правку всех строк.

**Уникальность без учёта регистра** - уникальный индекс по `lower(name)` в базе, а не только проверка в коде: два одновременных запроса не создадут дубль. Ошибка нарушения индекса превращается в «Группа с таким названием уже есть». Название хранится так, как ввёл пользователь. Длина 50 и «не пусто» - проверки zod плюс `check` в базе.

**Создание «на лету» в карточке.** Форма контакта получает отмеченные группы (`groupIds`, несколько значений) и список новых названий. Кнопка «Добавить» у поля «Новая группа» создаёт группу отдельным server action и возвращает её, форма сразу добавляет её в список отмеченных; при уже существующем названии (без учёта регистра) возвращается существующая группа. Так «Сохранить» отправляет только id уже существующих групп. Альтернатива - создавать группы при сохранении контакта: ошибки названий пришлось бы смешивать с ошибками остальных полей.

**Выбор групп без новой библиотеки.** Нативные чекбоксы в стиле проекта (токены дизайна) внутри `fieldset` с `legend` «Группы». Мультиселект из shadcn не ставим: правила проекта требуют обсуждать каждую новую библиотеку, а групп у человека обычно десяток.

**Сохранение связей.** `updateContact` и `createContact` в одной транзакции с остальными полями заменяют набор связей контакта: удаляют лишние, добавляют новые. В `getContact` и в данные формы добавляется `groupIds`.

**Список.** `listContacts` принимает `search` и `groupId`. Группы контакта приходят в той же выборке одним полем `groupNames` (`array_agg` по алфавиту ICU, как сортировка имён; подзапрос или `left join` с группировкой), без запроса на строку. Фильтр - `exists` по `contact_groups`. Поиск - `name ilike` **или** `exists` связанной группы с `groups.name ilike`. Фильтр по группе и поиск соединяются через И. `escapeLike` переиспользуется.

**Фильтр в адресе.** `?group=<id>` рядом с `?q=`. Неизвестный или некорректный id (нет такой группы, не число) трактуется как «Все группы», без ошибки. Выбор группы - `<select>` в форме поиска: меняется и отправляется вместе с запросом; `key` на форме, как у поиска сейчас, чтобы «Сбросить» очищал обе части. «Сбросить» очищает и поиск, и группу. Блок «Пора связаться» читает только `q` (скрыт при поиске, группой не фильтруется).

**Страница `/groups`.** Серверная страница со списком (название - ссылка на `/?group=<id>`, число контактов), формой «Новая группа», переименованием на месте (форма с полем и «Сохранить») и удалением через уже имеющийся `alert-dialog`, как удаление контакта. Ссылка «Группы» - рядом с кнопкой «Добавить контакт» на главной.

**Переименование.** Одним `update`; нарушение уникального индекса - та же ошибка. Смена только регистра проходит, потому что индекс сравнивает строку саму с собой.

**Тесты.** По правилам проекта сначала тест. Чистую логику (разбор и проверка названия группы, разбор `?group=`) покрываем Vitest-тестами. Vitest - часть стека, но в проекте пока не подключён: подключаем в первой задаче. Сценарии, которым нужны база и браузер, пока проверяются руками по списку в задачах; e2e на Playwright и CI настроим отдельным шагом по решению пользователя. Это сознательно отступает от правила конфига «у каждого сценария свой тест».

## Risks / Trade-offs

- `lower()` в Postgres зависит от локали базы: на кириллице работает, если база создана с UTF-8 и не `C`-локалью → проверить на локальной базе в Docker и на проде до выкатки: создать «Теннис» и «теннис».
- `array_agg` и `exists` в поиске замедляют список при тысячах контактов → индексы по `contact_groups`, замер на сидовых 1000 контактах; нужен заметно рабочий список как сейчас.
- Нет автотестов на сценарии с базой и интерфейсом до настройки e2e → ручная проверка по списку в tasks.md; риск регрессий до e2e принят.
- Удаление группы необратимо для связей (контакты остаются, но кто в ней был - не восстановить) → подтверждение с числом контактов.

## Migration Plan

Одна миграция Drizzle: две новые таблицы, индексы, `check`. Существующие данные не затрагиваются, по умолчанию групп нет. Применяется обычным отдельным шагом до нового образа. Откат вручную: предыдущий образ не знает про новые таблицы и продолжает работать, таблицы просто остаются.
