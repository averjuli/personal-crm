# Design

## Context

Зачем - см. `proposal.md`, требования - `specs/user-auth`, `specs/data-ownership`, `specs/contact-groups`.

Что есть сейчас:

- Входа нет. Все функции данных в `src/lib/contacts.ts` работают по всей таблице; server actions в `src/app/contacts/actions.ts` и `src/app/groups/actions.ts` проверяют только номер записи
- Таблицы `contacts`, `notes`, `groups`, `contact_groups` без владельца; уникальность названия группы - глобальный индекс `groups_name_lower_idx` по `lower(name)`
- Next.js 16 с `cacheComponents: true`: всё, что читает запрос (cookies, заголовки), должно рендериться внутри `<Suspense>`. Карточка контакта уже так устроена (`connection()` внутри `Suspense`)
- Шапка - `src/components/app-document.tsx`, она же используется в `global-error.tsx`, где сессию не прочитать
- Миграции: сервер запускает `scripts/migrate.mjs` (сборка `src/db/migrate.ts`) в разовом контейнере; локально `pnpm db:migrate` - это `drizzle-kit migrate`; тестовые базы мигрирует `testing/database.ts`
- Тесты: Vitest и Playwright на настоящих базах `<db>_test` и `<db>_e2e`; e2e-тесты правят базу напрямую для подготовки данных
- Сервер: nginx перед приложением ставит `X-Real-IP $remote_addr` и `X-Forwarded-For $proxy_add_x_forwarded_for`. Репозиторий публичный: личной почты в коде быть не должно
- Better Auth 1.7.x (последняя на сегодня 1.7.15), Nodemailer 10.x. Плагин magic link Better Auth: срок по умолчанию 5 минут, токен одноразовый, «новая ссылка гасит старые» сам не делает. Встроенный лимит по IP действует только на запросы из браузера, вызовы `auth.api` с сервера он не ограничивает

## Goals / Non-Goals

**Goals:**

- Ни одна функция данных не вызывается без владельца: фильтр по владельцу - в самом слое данных, а не в страницах
- Все правила входа (проверка почты, приведение к одному виду, лимит, погашение старых ссылок) живут в одном месте на сервере и действуют одинаково для формы и для прямого запроса к `/api/auth/*`
- Одна сборка приложения везде: всё, что отличает компьютер, CI и сервер, - в переменных окружения
- Миграция переносит все данные владелице в одной транзакции: либо всё, либо ничего

**Non-Goals:**

- Всё из «Не делать» спеки: пароли, соцсети, код из письма, профиль, удаление аккаунта, общий доступ, роли
- Возврат после входа на страницу, которую открывали до входа: после входа всегда главная
- Ограничение владельца в самой базе для связей контакт-группа (см. решение 5)
- Изменение nginx и общих настроек сервера

## Decisions

### 1. Better Auth с плагином magic link и адаптером Drizzle

- `src/lib/auth.ts`: `betterAuth` + `drizzleAdapter(db, { provider: "pg", usePlural: true })` + `magicLink(...)` + `nextCookies()` (чтобы server actions ставили и стирали cookie). Обработчик - `src/app/api/auth/[...all]/route.ts` через `toNextJsHandler`
- Таблицы Better Auth в `src/db/schema.ts`, по его документации для той версии, что поставим: `users`, `sessions`, `accounts`, `verifications`. `usePlural`: `user` - зарезервированное слово Postgres, и остальные таблицы проекта во множественном числе. Номера пользователей - текстовые, их выдаёт Better Auth
- `magicLink({ expiresIn: 15 * 60, storeToken: "hashed", sendMagicLink })`: хешированный токен - после утечки файлов хостера (инцидент 2026-10-17) копия базы не должна давать рабочих ссылок
- Сессия: `expiresIn` 30 дней, `updateAge` 1 день (срок продлевается при заходе, но запись в базу - не чаще раза в день), кеш сессии в cookie выключен - выход и истечение действуют сразу
- Новый пользователь создаётся плагином при первом входе (`disableSignUp: false`), имя - пустая строка: Better Auth требует поле, спека запрещает его спрашивать
- Ошибка проверки ссылки (использована, просрочена, погашена) - `errorCallbackURL: "/login/expired"`; Better Auth во всех этих случаях отдаёт `INVALID_TOKEN`, поэтому страница одна
- IP для встроенного лимита - из `X-Real-IP` (`advanced.ipAddress.ipAddressHeaders`): nginx ставит его сам, подделать нельзя, а `X-Forwarded-For` клиент может дописать

Альтернатива - свой вход на токенах в таблице: меньше зависимостей, но Better Auth задан спекой.

### 2. Правила запроса ссылки - в хуке Better Auth

`hooks.before` для пути `/sign-in/magic-link` - одна точка и для формы (`auth.api.signInMagicLink` из server action), и для прямого POST на `/api/auth/sign-in/magic-link`. По порядку:

1. Почта: `trim` + `toLowerCase`, проверка `z.email()` - общая функция `parseEmail` в `src/lib/email-address.ts`, её же вызывает форма до отправки. Неверный адрес - `APIError` `BAD_REQUEST` с кодом `INVALID_EMAIL`. Тело запроса подменяется приведённой почтой, поэтому пользователи и токены всегда с почтой в одном виде
2. Лимит: в транзакции под `pg_advisory_xact_lock(hashtext(email))` считаем строки новой таблицы `sign_in_emails` (почта, время отправки) за последние 10 минут; 3 и больше - `APIError` `TOO_MANY_REQUESTS` с кодом `TOO_MANY_EMAILS`; иначе добавляем строку и удаляем строки этой почты старше 10 минут. Блокировка - чтобы два одновременных запроса не прошли оба на третьем письме
3. Погашение старых ссылок: удаляем из `verifications` все записи magic link с этой почтой. Хук работает до того, как плагин создаст новый токен, поэтому новый не задевается. Как плагин хранит почту в `value`, проверяем на установленной версии тестом «Старая ссылка после запроса новой»

Время берётся из часов приложения (`new Date()`), не базы: так Vitest двигает время фейковыми часами, как уже делают тесты «Пора связаться».

Альтернативы: встроенный лимит Better Auth - считает по IP и пути, а не по почте; проверки в server action - не закрывают прямой запрос к `/api/auth`.

### 3. Письма: Nodemailer, транспорт из настройки

- `src/lib/mailer.ts`: `nodemailer.createTransport(process.env.SMTP_URL)`, отправитель - `MAIL_FROM`. Локально и в CI `SMTP_URL=smtp://localhost:1025` (Mailpit), на сервере `smtps://resend:<ключ>@smtp.resend.com:465`
- Текст письма - чистая функция `src/lib/sign-in-email.ts` (тема, HTML с кнопкой «Войти», текстовая версия); цвета в HTML письма - те же значения, что в дизайн-токенах, вписанные прямо в стили: почтовые программы не читают CSS приложения (так же сделан `deploy/unavailable.html`)
- Ошибка отправки (SMTP недоступен) - исключение: пользователь видит уже существующую страницу «Что-то пошло не так», новых текстов не вводим
- Mailpit: сервис в `compose.yaml` (SMTP `127.0.0.1:1025`, страница `http://localhost:8025`) и сервис в задаче Playwright в CI

### 4. Проверка входа: `proxy.ts` для удобства, слой данных для защиты

- `proxy.ts` (так в Next 16 называется middleware): нет cookie сессии - перенаправление на `/login`. Только для удобства, без обращения к базе. Исключения: `/login`, `/api/auth`, `/health`, статика
- Защита - `src/lib/session.ts`: `requireUserId()` читает сессию через `auth.api.getSession({ headers })`, без сессии - `redirect("/login")`. Её вызывает каждая страница с данными и каждая server action до любой работы с базой
- Все функции `src/lib/contacts.ts` получают `ownerId` первым параметром; каждый запрос фильтрует по нему: контакты и группы - по своей колонке, заметки и связи - через контакт. Чужая запись выглядит как несуществующая: функции возвращают тот же `false` / `undefined` / `"not-found"`, что и сейчас
- Шапка: `AppDocument` получает необязательный слот справа; корневой layout кладёт туда `<Suspense>` с почтой и кнопкой «Выйти» (server action `signOutAction` → `auth.api.signOut` → `/login`). `global-error.tsx` слот не передаёт
- `/login` и `/login/expired` - страницы без данных; вошедшего `/login` отправляет на главную
- `src/app/contacts/[id]/not-found.tsx` - «Контакт не найден» для несуществующего и чужого номера; общая «Такой страницы нет» остаётся для остальных адресов

### 5. Модель данных

- Новые таблицы: `users`, `sessions`, `accounts`, `verifications` (Better Auth), `sign_in_emails` (`id`, `email`, `sent_at`, индекс по `email, sent_at`)
- `contacts.owner_id` и `groups.owner_id`: `text not null references users(id)`, без каскадного удаления - удаления аккаунта нет. Индекс по `owner_id` у обеих
- Уникальность групп: `groups_name_lower_idx` заменяется на уникальный индекс `(owner_id, lower(name))`
- `notes` и `contact_groups` без владельца: заметка принадлежит владельцу контакта (так в спеке). Что контакт и группа связи одного владельца, проверяет `setContactGroups`: берёт только группы этого владельца

Альтернатива для связей - составные внешние ключи `(contact_id, owner_id)` и `(group_id, owner_id)`: защита в базе, но лишняя колонка и индексы ради случая, который уже закрыт кодом и тестом «Чужая группа у своего контакта».

### 6. Миграция данных и почта владелицы

- Одна миграция `0003`: drizzle-kit генерирует таблицы и колонки, руками дописываем перенос. Порядок: таблицы → колонки владельца без `not null` → если есть контакты или группы: почта владелицы из настройки сессии Postgres `crm.owner_email`, пустая - `raise exception` с понятным текстом; пользователь с этой почтой (создаём, если нет) → `update` владельца у всех контактов и групп → `not null` → замена индекса групп. Drizzle применяет все новые миграции в одной транзакции, поэтому при ошибке база остаётся как была
- Откуда настройка: новая функция `applyMigrations(client, ownerEmail)` в `src/db/migrations.ts` перед миграциями выполняет `set_config('crm.owner_email', ...)` на том же единственном соединении. Её вызывают `src/db/migrate.ts` (сервер и теперь локальный `pnpm db:migrate`: скрипт меняется с `drizzle-kit migrate` на `tsx src/db/migrate.ts`, таблица истории та же) и `testing/database.ts`
- `OWNER_EMAIL` из окружения приводится `parseEmail`; задан, но неверный - миграция падает до изменений. Тестовые базы получают фиксированную тестовую почту, не настоящую
- Демо-данные (`src/db/seed.ts`) берут ту же `OWNER_EMAIL`: находят или создают пользователя и создают контакты у него; без настройки - понятная ошибка

Альтернативы обсуждены с пользователем: почта в коде миграции (попадает в публичный репозиторий), «первый вошедший» (данные может забрать друг). Выбрана настройка в `.env`.

### 7. Настройки окружения

| Настройка | Компьютер | CI | Сервер |
| --- | --- | --- | --- |
| `BETTER_AUTH_SECRET` | `.env` | тестовое значение в workflow | `/opt/personal-crm/.env` |
| `BETTER_AUTH_URL` | `.env`: `http://localhost:3000` | e2e: `http://localhost:3100` | `deploy/compose.yaml`: `https://app.vupsen.space` |
| `SMTP_URL` | `.env`: Mailpit | Mailpit | `/opt/personal-crm/.env`: Resend (в строке ключ) |
| `MAIL_FROM` | `.env` | workflow | `deploy/compose.yaml`: `Личная CRM <noreply@mail.crm.vupsen.space>` |
| `OWNER_EMAIL` | `.env` | не нужна: базы пустые | `/opt/personal-crm/.env` |

- Playwright запускает приложение со своими `BETTER_AUTH_URL` и `SMTP_URL`, как сейчас со своей `DATABASE_URL`
- `deploy/compose.yaml` передаёт настройки и приложению, и разовому контейнеру миграций и демо-данных (это тот же сервис `app`); обязательные - через `${VAR:?...}`, поэтому без них выкатка падает на первом же шаге, до бэкапа, а старая версия продолжает работать
- Сборка образа: `Dockerfile` даёт сборке заглушку `BETTER_AUTH_SECRET`, как сейчас `DATABASE_URL`; настоящие значения в образ не попадают

### 8. Тесты

- Vitest, настоящая база: слой данных от имени A и B (каждый сценарий `data-ownership` и изменённых `contact-groups`); правила входа через `auth.api` и `auth.handler(new Request(...))` для прямых запросов, с подменой `src/lib/mailer.ts` на сборщик писем и фейковыми часами `Date` для 15 и 10 минут; миграция `0003` на копии старой схемы с данными (временная папка миграций с журналом до `0002`, затем все); `parseEmail`, текст письма
- Playwright, без моков: письма из Mailpit через его API (поиск по адресу получателя; адреса уникальны на каждый запуск, ящик не чистим - он общий с разработкой). Критерий успеха спеки - отдельный тест `e2e/two-users.spec.ts`: A и B в двух браузерах, каждый добавляет контакт и не видит контакта другого ни в списке, ни в поиске, ни по прямой ссылке. В `e2e/auth.spec.ts`: старая ссылка - срок токена сдвигается прямо в базе, как другие e2e готовят данные; лимит, неверная почта, выход, шапка
- Остальные e2e (главный сценарий из `specs/01`, группы, «Пора связаться») входят один раз в setup-проекте Playwright и берут сохранённую сессию (`storageState`); `resetDatabase` создаёт контакты у этого тестового пользователя. Главный сценарий во «втором браузере» входит под тем же пользователем

## Risks / Trade-offs

- [Хостер блокирует исходящие SMTP-порты] → до выкатки проверить с сервера соединение с `smtp.resend.com:465`; запасные порты Resend - 2465 и 2587, меняется только `SMTP_URL`
- [Почтовая программа или антивирус открывает ссылку раньше человека и «съедает» одноразовый токен] → человек увидит «Ссылка устарела» и запросит новую; Gmail так не делает. Если начнёт мешать - вернусь с вопросом
- [Встроенный лимит Better Auth по IP (5 запросов в минуту на проверку ссылки) срабатывает в e2e: сборка запускается как прод] → входить в e2e как можно реже (setup-проект, сессия сохраняется), сценарии с многими входами проверять в Vitest через `auth.api`, который лимитом не ограничен. Если не хватит - спрошу, а не выключу лимит молча
- [Строка в `sign_in_emails` пишется до отправки: упавшая отправка тоже считается в лимите] → редкий случай, пользователь подождёт 10 минут; зато лимит не обходится одновременными запросами
- [Сессия продлевается не чаще раза в день] → вход держится от 29 до 30 дней после последнего захода, а не ровно 30
- [`proxy.ts` пускает со старой cookie, хотя сессия уже кончилась] → это только перенаправление; страницы и actions всё равно проверяют сессию в базе и отправляют на вход
- [Откат только кода после этой выкатки ломает старую версию: в `contacts` новый `not null` `owner_id`, и старая версия не сможет добавить контакт] → откат - только вместе с базой, порядок ниже и в README

## Migration Plan

Перед merge:

1. Показать пользователю миграцию `0003` (меняет существующие данные) - правило CLAUDE.md
2. Пользователь (только человек): аккаунт Resend, домен `mail.crm.vupsen.space`, записи DNS, которые покажет Resend, ключ только на отправку
3. Пользователь добавляет в `/opt/personal-crm/.env` строки `BETTER_AUTH_SECRET`, `SMTP_URL`, `OWNER_EMAIL` - скажу, какие и какой командой сделать секрет; права файла остаются 600
4. Проверить с сервера доступность `smtp.resend.com:465`

Выкатка - как обычно, merge в main: бэкап → миграции (перенос владелице) → новая версия → smoke `/health`. Проверка после:

- контактов, заметок, групп и связей столько же, сколько в бэкапе перед выкаткой (команды подсчёта дам)
- вход по ссылке под своей почтой - все прежние контакты на месте; вход под другой почтой - пустой список

Откат (только вручную, запускает пользователь):

1. `ssh crm sudo crm-deploy rollback` - прошлая версия приложения
2. `ssh -t crm sudo crm-deploy restore <копия prod-…, снятая первым шагом выкатки входа>` - база до выкатки, приложение той же (прошлой) версии

Данные, добавленные после выкатки, при откате пропадут. Этот порядок записывается в README.
